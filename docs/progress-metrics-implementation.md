# Progress metrics implementation

Requirements source: [iOS handoff](progress-metrics-handoff.md). Backend scope only; the native app continues to use its offline snapshot until its canonical date/identity migration and reconciliation are implemented.

## Plan

1. Add backward-compatible canonical date provenance, optional client logging instant and actual session duration, and explicit strength load convention. Keep writes in revisioned sync.
2. Implement versioned pure calculations for actuals, logical-result deduplication, daily totals, journey, revocable milestones, and exact comparisons. Use stored training dates and calendar-day arithmetic.
3. Persist daily/activity/comparison projections. Coalesce invalidations into a transactional per-athlete outbox; drain it under the same athlete lock used by sync. Rebuild all affected history atomically, including old dates, former bests and revoked achievements. No extra dev container is needed.
4. Expose the three authenticated read APIs, bounded chart previews, signed revision-bound cursors, private ETags and midnight/timestamp expiration. Account deletion cascades through projections and caches.
5. Generate OpenAPI; exercise native-style fixtures, canonical migration differences, real PostgreSQL mutation/replay/deletion/pagination behavior, and a repeatable 10,000-result benchmark. Run the complete existing test suite and leave only API/Postgres dev containers running.

## Decisions

- Schema/rules version 1 explicitly uses the stored `trainingDate`. `dateBasis` defaults to `performedDate` for existing canonical records. Legacy native uploads must send `loggedDate`, the known local logging date/timezone, and optional `loggedAt`; they must not copy a planned date or invent start/end instants. `durationS` is optional actual session duration; running uses `run.durationS`, strength uses this field or known start/end elapsed time, otherwise zero with a missing-duration flag.
- Logical identities are deduplicated before eligibility. Latest canonical sync sequence wins, with `updatedAt`, revision and result ID as deterministic fallbacks for pre-sync records. This is a server commit ordering, deliberately different from trusting device clocks. A latest skipped result suppresses older results; deleted results are removed before selecting the live head. Null logical IDs remain distinct.
- Valid completed sets use native v1 bounds (1–100 reps, finite 0–1,000 kg), including warmup/backoff and bodyweight zero. Canonical sync retains its wider storage bounds; out-of-metric-range sets are excluded with reasons. `loadConvention` defaults to `external`; explicit bodyweight is separate. Assisted sets count toward volume but are excluded from v1 comparisons because increasing assistance is not increasing strength.
- Exact historical prescription types map identically for `easy`, `recovery`, `long`, `tempo`, `intervals`, `hills`, `progression`, `custom`. Other strings and absent prescriptions map to `custom`; titles are never classified.
- Comparisons require two distinct stored training dates. Running compares completed actual distance ≥1,000 m, exact meters/type and elapsed seconds/km. Strength compares actual canonical exercise ID, reps and load convention, using the heaviest completed set per session. First/latest order is training date, known occurrence/logging instant, then result ID. Group selection uses latest canonical logging order, with group-key tie breaking. Exact best/first/latest remain independent of at most 32 representative chart points.
- Projection refresh is synchronous on a read when dirty; a successful read therefore has equal source/projection watermarks and `freshness:current`. Failed rebuilds roll back and return the standard error envelope; no partial snapshot is served. The outbox is durable, coalesced and replay-safe. Full per-athlete recalculation with changed-row persistence favors correctness for corrections/deduplication; measured costs and a future incremental worker boundary are documented below after validation.
- No historical `asOf` input. The response states when it was calculated. Cursor scope includes athlete, endpoint/query, projection generation and local day; edits, due timestamps and midnight invalidate it with HTTP 409. Page size is 1–100; activity windows are at most 366 calendar days and can be traversed across multiple windows.
- Private summary cache entries are bounded per athlete and expire at local midnight or the next known future actual instant, whichever comes first. Every request revalidates authentication and canonical watermark; logout/deletion cannot reuse a fresh browser response without authorization.

## Validation results

The repeatable benchmark (`make progress-benchmark`) uses real authentication, Bun HTTP loopback with gzip, PostgreSQL 17, 10,000 results, 60,000 completed sets, 10,000 source records and 20,000 canonical sync events. Twenty requests after actual corrections measure complete canonical recalculation and changed-row projection persistence; 50 requests measure the private summary cache. Database pages are warm and requests are serial. This is a local measurement, not a production or concurrency SLA.

Measured September 22, 2026: cached p95 **5 ms**; recalculation after edits p95 **430 ms**; initial materialization **547 ms**; compressed 84-day summary **3,898 bytes**. The first materialization exceeds the proposed 500 ms target; subsequent edit refreshes and cached reads meet their proposed p95 budgets in this run. [Raw measurements and query plans](progress-metrics-benchmark.json) are checked in. The benchmark explains the exact production canonical queries: result loading took 9.849 ms, set aggregation 77.670 ms, and source aggregation 3.057 ms. PostgreSQL chose sequential/hash plans for these full-history reads in the single-athlete fixture. The existing `results_owner_date_idx` remains available; `progress_activity_page_idx` served the bounded history query in 0.182 ms. No speculative extra canonical indexes were added. Multi-athlete load plans still need production measurement.

Projection persistence upserts only changed rows and removes rows no longer eligible. It avoids rewriting an athlete's entire history after each edit while retaining full recalculation for correct logical deduplication, first crossings, day moves and revoked bests. Work remains synchronous under the athlete lock; substantially larger histories or high write concurrency may require incremental recomputation and a background worker. There is no worker container in the MVP.

Unit fixtures mirror the native checks for actual-only volume, bodyweight/partial work, logical duplicates, calendar windows, lifetime milestones and exact comparisons. Separate fixtures cover deliberate migration differences: canonical exercise IDs, authoritative performed dates while traveling, legacy logged dates with unknown instants, and canonical sync sequence ordering instead of device clocks. This does **not** claim that today's unmodified native model has byte-for-byte server parity.

`make check` passed 63 tests (29 unit/provider and 34 PostgreSQL/auth integration), plus lint, typechecking and OpenAPI drift checks. The separate 10,000-result benchmark also passed. The production Docker image builds successfully.

Integration checks cover real authentication and sync, aggregate set replacement, failed mutation rollback, source matching/deletion, outbox replay/lag and crash recovery, consistent concurrent reads, correction/deletion, account isolation/purge, conditional caching, future instants, midnight and revision-bound pagination.

## Client contract

- `GET /v1/progress/summary?periodDays=28&timezone=America/Monterrey` returns named `ProgressSummary`. Periods are 7, 28 and 84. There is no `asOf` request parameter.
- `GET /v1/progress/comparisons/{comparisonKey}?timezone=America/Monterrey&limit=50` returns named `ProgressComparisonPage`, with the same exact first/latest/best as the summary and at most 100 history points per page.
- `GET /v1/progress/activity?from=2026-10-01&to=2026-10-31&timezone=America/Monterrey&limit=50` returns named `ProgressActivityPage`. Dates are inclusive. Repeat the identical query with its opaque `cursor`; restart on `409 PROGRESS_CURSOR_EXPIRED`.
- Timezone defaults to UTC. Clients should always pass their current IANA timezone to all three endpoints. This selects today's cutoff and cache expiry; it never moves a stored workout's local training date.
- Revalidate summaries with `If-None-Match`. The server supports gzip and returns a private ETag; compressed variants use a weak ETag. HTTP 304 has no body. History responses remain `private, no-store`.
- `dataRevision` and `projectionSequence` are decimal strings containing the latest progress-relevant canonical sync sequence, not an all-entity sync acknowledgement cursor. Other entity mutations need not change these watermarks. Successful reads drain pending projection work and return `freshness:current`.
- `earnedOn` is the authoritative threshold-crossing date; `earnedAt` may be null when the actual instant is unknown. Never replace null with upload time. `dateBasis` summarizes eligible lifetime actuals (`performedDate`, `loggedDate`, or `mixed`); each activity carries its own basis and timezone.
- `activeSeconds` uses recorded elapsed activity duration, not moving time. A strength result with neither actual duration nor known start/end contributes zero seconds and a `missing_duration` flag, while its valid completed sets still count.
- Summary comparison previews contain at most 32 representative points; exact first/latest/best and sample counts are independent of sampling. `hasMore` indicates omitted chart points. History is lifetime data regardless of the selected summary period. Unsupported or absent run types are explicitly `custom` and marked in activity provenance.
- Stable milestone keys match native v1 names. Percent changes are null when the denominator is zero. Journey counts distinct eligible training days, not streaks.
- Provenance flags describe eligible activity; `exclusions` describes filtered results/sets and unresolved sources. Source records never add volume by themselves. Unresolved imports remain distinct canonical results until sync resolves their logical identity; the server does not guess matches.

Canonical sync adds optional `dateBasis`, `loggedAt`, and session `durationS` on workout results, and `loadConvention` on strength sets (`external`, `bodyweight`, `assistance`). Older payloads default to performed-date provenance, unknown logging/duration instants, and external load. Running session duration, when supplied, must equal `run.durationS`. Prescriptions remain immutable. Regenerate clients from [OpenAPI](../contracts/openapi.yaml).

Before enabling these endpoints in the iOS UI, its agent must persist canonical training dates/timezones, revisions and exercise IDs, label legacy logging dates explicitly, and choose one authoritative local/server snapshot per render. An offline overlay must account for replacement/deletion deltas rather than add all local totals to server totals. Logout clears native summaries; server account deletion cascades through every derived table and cache.
