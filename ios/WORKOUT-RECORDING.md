# Live workouts

The native iPhone and Watch apps now contain an outdoor running recorder and focused resistance logger. Builds and deterministic checks pass; physical-device validation below remains required before treating this as a production recorder.

## Athlete flow

- Open a planned run and choose **Record on iPhone** or **Use Apple Watch**. Watch instructions send the current plan; open hybrd on the paired Watch and explicitly start the chosen run there. Plan receipt should complete before leaving the phone behind. This is explicit device ownership, not a remote-start or live-mirroring implementation.
- Watch offers three horizontally paged views, opening in the center: controls on the left (pause/resume, lap, confirmed stop/finish), live pace/heart rate/zone with active time and distance in the center, and next interval plus workout description on the right. Resuming returns to metrics after the native session confirms the state change. Ending requires confirmation. Lowered-wrist rendering reduces the UI refresh cadence; recording remains managed by the native workout session.
- iPhone has a large live pace readout, interval guidance, fresh HR/zone when available, distance/time/average pace, recent splits and bottom controls. Minimize keeps recording; a persistent return banner opens the active run. Manual completed-run entry remains available.
- Native sessions collect heart rate on Watch. iPhone needs a supported external heart-rate sensor available through Apple Health; this change does not add a Bluetooth-pairing UI or stream Watch HR into an iPhone-owned workout. No sensor data is simulated in the app. Missing/stale HR displays a dash after 20 seconds. Personal BPM boundaries come only from the athlete profile, including its cached copy on Watch.
- Guidance expands existing timed run segments into chronological work/recovery repetitions. Timers exclude pauses. Next interval advances guidance without adding performed time/distance. The run continues after the prescription ends until the athlete finishes. Manual laps and automatic kilometer splits are separate lists; boundaries use interpolation between distance samples. Watch gives interval/lap haptics. No auto-pause, spoken coaching, indoor calibration, cycling mode or race prediction is implemented.
- Finish retains a reviewable local checkpoint and attempts an Apple Health workout/route save. Review displays actual distance/time/pace, available HR summaries, segmented route and laps. Zero-distance records can be discarded and manually logged; they are not saved as invented workouts. Health-save failures leave the local measurements available and disclose the failure.
- Resistance uses one selected exercise with direct weight/reps input, optional 0–10 RIR (10 means 10+), previous set values, explicit completed-set toggles, added/removed sets, and next-exercise navigation. RIR is separate from prescribed target RIR and optional session effort. Completed sets start a rest countdown. Rest deadlines persist in the draft, with +15 seconds/skip and optional local alerts. Notification authorization occurs only after enabling alerts; no remote push service is used. Strength results are saved in hybrd, not written as Apple Health workouts in this version.

## Sources and durability

`RunRecorder` lives at app scope rather than in a screen. Both platforms use `HKWorkoutSession`/`HKLiveWorkoutBuilder`, native Core Location and just-in-time authorization. Phone distance is derived from accepted GPS fixes and is added once to the Health builder; its automatic distance source is disabled to avoid double counting. Watch distance uses the live workout builder's native distance metric. Current pace uses smoothed valid GPS speed; displayed values identify unavailable GPS. Native platform estimates may differ from a surveyed course and require field validation.

`RunGPSFilter` rejects invalid coordinates, stale/out-of-order fixes, >25 m accuracy, implausible >12 m/s displacement and sub-3 m jitter. It does not bridge pauses or gaps longer than 15 seconds. These are initial conservative filters, not a calibrated performance claim. GPS gaps can reduce recorded phone distance. Route points are thinned to at least three seconds apart while distance processes accepted fixes; segment starts are retained. The 30,000-point route cap is disclosed if reached. Route display in hybrd separates gaps; Apple Health receives timestamps and workout pause events.

Every five seconds and on state transitions, atomic metadata is checkpointed in Application Support. Route points append to a protected journal so the full route is not rewritten each checkpoint. Checkpoint files use file protection until first unlock. A relaunch attempts native active-session recovery; if it fails, local timing is paused at the last durable checkpoint rather than counting unobserved downtime. Recovery during finalization checks the existing Health workout external UUID before attempting the recovered builder, and does not create a new replacement Health workout blindly. Unreadable active checkpoints are preserved and block overwrite. Storage errors are surfaced.

Watch saves a completed recording into its durable file outbox before clearing the active run. `WCSession.transferFile` supports full route payloads without placing them in the small user-info payload. iPhone stores the received file in its inbox, validates basic actuals, and writes the canonical local result transaction before returning an application receipt. Transport delivery alone does not clear the Watch outbox. Retry on reachability/app activation and explicit Retry transfer is idempotent by recording UUID. A second result for the same logical prescription waits for explicit review: keep as a separate actual or dismiss an already-recorded duplicate. Both real runs can be retained without double-counting a retried delivery. These paths are implemented but real paired-device transfer remains unverified.

`WorkoutResult.run`, `LoggedSet.rir`, `WorkoutDraft.rest` and personal-zone snapshot metadata are optional for backward-compatible decoding. Recording UUID is the result UUID. Exact physical/logical prescription IDs remain attached. Live runs have no invented RPE: the legacy effort slot is zero/unreported and the detail UI omits it. The recorded run retains actual start/end instants and recording timezone; legacy Progress still groups the completed result's logged/end date until the canonical performed-date migration is integrated.

## Backend integration contract

Continue using the existing revisioned `workout_result` sync aggregate. No new backend write endpoint is required for this local feature. This work does not add server authentication or upload routes.

- Map stable recording ID to result ID; retain physical and logical prescription IDs. Use recorded start/end, explicit performed `trainingDate` and `recordedTimeZoneID` rather than upload time or a planned date. Resolve overnight/travel date policy in the canonical migration.
- Map actual distance to integer `run.distanceM`, active duration to `run.durationS` with a documented duration basis, and available HR summaries to nullable fields. Do not label active time as moving time. Send unreported effort as null where supported, not an invented RPE of 5. Personal HR zone targets are prescriptions, not measured zone-duration summaries.
- Completed-set `rir` maps to the canonical nullable set RIR. Preserve zero (no reps left) and nil (unreported), actual substitutions, extra sets and exact prescription links. Incomplete sets are not sent as completed work. RIR 10 is the app's 10+ display bucket.
- Preserve lap kind/sequence/time/distance as actual segment/split information only when the canonical contract can distinguish manual laps from automatic kilometer splits. They overlap and must not be summed into workout totals. Planned intervals skipped in guidance are not completed actual segments.
- Apple Health `healthWorkoutID` and the recording external UUID are provenance/deduplication inputs. A later Health import of the same workout must match the existing result rather than create another run. Preserve source-link deletions independently of actuals, consistent with the current handoff.
- Do not send the full `RunRecording` JSON as the backend result payload. It contains a local route journal representation. The existing canonical sync contract excludes raw sensor traces; route/HR time-series upload requires a separately reviewed bounded storage/consent contract. Current routes stay on device and, when permitted, Apple Health.
- Workout corrections should invalidate the Progress projection using existing revision/outbox rules; transfer receipts and UI state never mutate immutable prescriptions.

## Watch refinement and crash investigation — 22 September 2026

The workout list now uses the existing original shoe/dumbbell illustrations, run-category colors, a prescribed interval profile, and a set-count graphic. The five-zone live strip outlines/dots the actual zone and underlines the target's label; the explicit target/BPM caption keeps the two distinct. It never computes personal boundaries from age or prescription. Missing/stale/paused HR leaves the actual zone unselected. The next-interval page shows countdown, repetition, zone target and cue before the complete workout description. Native horizontal paging and named accessibility actions navigate the three pages; vertical content remains scrollable.

Crash reports `hybrd Watch-2026-09-22-155902.ips` and subsequent launch reports through `160031.ips` show SIGABRT from `_swift_reportExclusivityConflict`, in `RunRecorder.finishCollection(at:)`. The first path simultaneously modified `recording` and read `recording.elapsed` (old line 255). Recovery reached a second instance while setting the error message based on `recording.healthWorkoutID` (old line 281). Both reads now occur inside mutating methods on the recording value, avoiding nested access to the `@Observable` optional. No saved workout or Health data was deleted to escape the crash loop.

Regression checks invoke both finalization operations through an observed optional, assert distance/timing and both save-failure states, and cover current/next guidance at exact interval boundaries, pauses, empty prescriptions and completion. Bitrig's iPhone/Watch build succeeds. The recovered 0.09 km / 34-second run remains in the simulator accessibility tree; no new hybrd Watch crash report appeared during this validation. Bitrig screenshot requests return “The simulator couldn't start” and scrolling did not update its accessibility tree, so native swipe/control interaction is not claimed as verified. Temporary macOS renders of the actual view sources were reviewed at compact/large widths and paused/missing-data states; macOS does not establish watchOS Dynamic Type behavior. Full hardware acceptance above still applies.

## Watch start navigation fix — 22 September 2026

A run started from the pushed workout detail could record while the detail stayed visible: switching the root content inside the existing `NavigationStack` did not remove its pushed destination. The recording/list branch now sits outside the stacks. Creating or restoring a recording replaces the entire plan navigation stack with the run stack, whose pager defaults to center metrics. Clearing the recording recreates the plan stack without a stale detail page. Start/permission errors appear directly beside Start run rather than below the entire prescription.

Validation: reproduced an unchanged Start run screen after tapping Start; the Bitrig build passed with no diagnostics. After rebuild, the native Watch accessibility tree showed the active warm-up, elapsed time, distance, HR and “page 2 of 3,” with no Start run destination covering it. This verifies the active-run presentation; it does not add a claim of new hardware sensor or permission-flow coverage.
